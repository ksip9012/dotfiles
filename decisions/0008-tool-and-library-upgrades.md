# 0008. mise・uv・ライブラリの上げ方を決める

- Status: Accepted
- Date: 2026-11-03

## Context
言語の版の選び方は 0007 で決めたが、ほかの版の上げ方は決まっていなかった。2026-11-03 時点で次のようになっていた。

- mise 本体は Homebrew で入れていて、`mbrew` のたびに最新になる。CI の `jdx/mise-action` は、出て 24時間たった最新を入れる
- プロジェクトの uv は `mise.toml` に細かい版まで固定（ひな形 0.13.6、試作のリポジトリ 0.11.8）
- プロジェクトの外の道具（`mise/config.toml`）は uv 0.11.8・Node 25.0.0 に固定、Python は `latest` と古い 3.11.5・3.12.1。`mbrew` は mise で入れた道具を上げないので、uv がひな形より古いままになっていた
- ライブラリは `uv.lock` で、入れたときの版に固定されたまま。上げる時期は決まっておらず、セキュリティの問題だけ Dependabot が PR を出す（0005）

## Decision
1. mise 本体: Homebrew の `mbrew` で最新を追いかける
2. プロジェクトの uv: `mise.toml` に細かい版まで固定する。ひな形は毎年 11月、既存のリポジトリは触るときに上げる（0007 と同じ時期）。上げるときは `pyproject.toml` の `uv_build` の範囲も一緒に直す
3. プロジェクトの外の道具: `mise/config.toml` を `python = "latest"`・`uv = "latest"`・`node = "lts"` にし、`mbrew` で `mise upgrade` を動かして一緒に上げる。プロジェクトの外は最新、中は固定と役割を分ける
4. ライブラリ（アプリのライブラリと開発の道具）: 作業を始めるときに、両方一緒に上げる。本来の作業とは別のコミット（か PR）に分け、`mise run upgrade`（`uv lock --upgrade` → `mise run check`）を最初に回す。よく触るリポジトリは月 1回まで。触らないリポジトリは、セキュリティの問題だけ Dependabot に任せる。`pyproject.toml` には下限だけを書き、固定は `uv.lock` に任せる

## Consequences
- mise は版を管理する土台なので、新しいほうが新しい言語の版や `mise-action` とそろう。mise の版はプロジェクトの `mise.toml` では決められない
- uv は依存を解決する仕組みそのものなので、固定すると手元・CI・ほかの PC で `uv.lock` の結果がそろう。`latest` にすると `uv_build` の範囲を外れて急にビルドが通らなくなるので選ばなかった。マイナー版までにする案も、uv が 0.x で同じマイナー版でも動きが変わりうるので選ばなかった
- プロジェクトの外の道具は、決まった版でそろえる必要がないので、最新を追いかけても困らない。`mise upgrade` は今入っている道具を条件の中で最新にし、古い版は `upgrade.prune_after` の猶予のあとに消す。書き方を変えた道具は、最初に 1回 `mise install` が要る
- ライブラリを別のコミットで上げるので、開発の道具の変化（ruff の新しいルール、pyright の厳しくなった型の見方など）が本来の作業に混ざらない。月 1回の上限で、変化が一度にたまりすぎず、毎回の手間も増えすぎない
- 選ばなかった案: Dependabot の版の更新（PR が増える。0005）、開発の道具だけ毎年 11月に上げる（ひな形には `uv.lock` がないので作った日に最新が入る。既存のリポジトリを毎年触ることになり、0007 の「触るときに上げる」とぶつかる）
